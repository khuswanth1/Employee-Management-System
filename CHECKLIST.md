# Delivery checklist

Legend: ✅ implemented **and exercised by an automated test or an actual run** · 🟡 implemented, verified only partly · ⛔ not done / not verified

Environment used for verification: Windows, Python 3.14, Node 24. **Docker was not available**; the default tests and the manual browser run used SQLite tenant databases. A later pass ran the backend suite and provisioning against a local PostgreSQL 18 (no Docker).

## Organisation management (branches, managers, board, communication)
Implemented and covered by `backend/tests/test_org.py` (14 tests) plus the API/UI checks listed. Statuses are honest: anything not listed as done is not done.

- ✅ **Branches / locations**: founder creates, edits, deactivates, deletes (refused while people are assigned) and assigns employees, HR and managers; unique name/code; counts per branch; audit-logged. UI (`/branches`, founder only; HR no longer has the page, only the branch names in the employee filter) clicked through as founder: create, assign, unassign, delete.
- ✅ **Employee records**: employee ID (auto `EMP-0001` or custom unique), name, email, phone, designation, department, branch, work location, joining date, reporting manager (must share the branch). Add / view / edit / delete (delete only for accounts without history, otherwise offboard) with confirmations. UI checked as founder (fields, photo, delete) and as HR: **Activate** (onboarding -> active, with confirmation) and **Cancel** (discards unsaved profile edits; Save is disabled until something changes).
- ✅ **Employee photos**: HR/founder upload, replace and remove (with client-side preview before saving), employees manage their own; JPEG/PNG/WebP magic-byte check, 2 MB, stored per tenant, served only to signed-in users of the same company, audit-logged. UI preview + upload checked in a browser, including the optional photo picker in the Add employee form (preview, wrong file types rejected, saved right after the account is created; if the photo upload fails the employee is still created and the user is told to add it from the profile).
- ✅ **Branch scope** (HR with a branch, managers with a branch): employee list/detail/edit/documents/photos/delete, leave requests + decisions, attendance + update reports, CSV exports, dashboard counts, project visibility/membership and audit logs. Covered by tests for lists, direct-object access (404), leave and attendance.
- ✅ **Manager management** (`/managers`, founder only): branch, department, reporting line (cycle-safe), team assignment and four permissions (`projects.manage`, `leave.approve`, `updates.review`, `reports.view`) enforced server-side; verified that removing a permission gives `403` on the matching endpoints. UI Configure + reset-to-defaults checked in a browser. The **Team** dialog was only API-tested.
- ✅ **Board members** (`/board-members`, founder only): create, view, edit, deactivate, delete, designation, responsibilities, term, permissions. They see only aggregated analytics and a headcount CSV; every employee-level endpoint is `403`/`404` for them (tested against ~20 endpoints, plus photos and the leave calendar). UI create/edit/delete and the restricted board login/menu checked in a browser.
- ⛔ **Financial summaries for the board**: not implemented. WorkSphere has no financial data model; the analytics page says so instead of showing numbers. "Strategic reports" are limited to the headcount-by-branch/department CSV.
- ✅ **Communication hierarchy**: employee <-> manager/HR (same branch), peers (same branch), manager/HR <-> founder, founder <-> board; employee <-> founder blocked by default with founder-managed exceptions (UI: Chat > Direct lines, checked in a browser); rules re-checked on every send, groups reject forbidden pairs, the chat directory only lists allowed people.
- 🟡 **Founder UI trimmed on request**: the founder no longer gets the My Tasks, Daily Updates, Projects, Leave and Escalations pages (menu, routes and dashboard links; founder dashboard hides personal task/update cards). Side effects: a founder cannot open the Escalations page, so escalations that reach the founder can only be resolved through the API until a founder-facing page exists, Every role can view the company holidays on a **Holiday calendar** page (`/holidays`): a month calendar (holidays highlighted, weekends shaded) and a yearly list. Founders and HR edit there (click a weekday to add, a holiday to edit, list buttons to remove; weekends refused); managers and employees get it read-only. Checked in a browser against an isolated throwaway backend as founder (add by click, edit, list) and as an employee (read-only). Backend permissions are unchanged.
- ✅ **Team management & project allocation** (migration 0005, `/teams`, `modules/teams`): managers (permission `teams.manage`) and founders create/edit/delete teams, appoint or replace the leader, add/remove members and allocate projects they own; HR manages memberships and transfers inside their branch; the leader distributes tasks to team members only, tracks daily updates/blockers and reports to the manager; members flag blockers on tasks. Team progress, milestones, overdue/blocked work and per-team productivity (`/teams/analytics`) are computed server-side. Access is role- and branch-scoped (teams out of scope look non-existent), every change is audited (`team.*`). API-tested in `tests/test_teams.py` (permissions, branch rules, one-team-per-person, leader replacement, task distribution limits, blockers, transfers incl. cross-branch, offboarding, deactivation, deletion, tenant isolation). UI walked through in a browser against an isolated throwaway SQLite backend as manager and as team leader (list, overview, members, projects, updates, reports, leader's task dialog lists only team members). **Not verified:** the UI as HR/plain member/founder in a browser, the Postgres tenant path for migration 0005 (it follows the same pattern as 0001-0004 and `server_default=sa.false()` is Postgres-safe, but it has only run on SQLite), and the `chat` "Message" link just opens Chat (no pre-selected conversation).
- ✅ **Escalations**: employee -> manager or HR -> (escalate with note) -> founder -> resolved, notifications at each step, branch-scoped HR visibility, managers escalate to HR. Full chain run through the UI (employee creates, manager escalates, founder resolves) and API-tested.
- ✅ **Audit log** entries for employee create/update/delete/offboard, photo upload/removal (own and others'), profile edits, branch changes/assignments, manager/permission changes, board member changes, chat exceptions, escalation steps. Branch HR sees only events by people of their branch.
- ✅ Migration `0004` (plus `0002`, `0003`): upgrade, downgrade and re-upgrade verified on SQLite with existing users (employee IDs backfilled). The whole backend suite also passes against PostgreSQL 18 with the non-superuser provisioner role.
- 🟡 **Department-based permissions**: *not implemented as an access rule*. Departments are an attribute (filters, reports, a manager's configured department) but no endpoint restricts access by department. Scope is company + role + branch + reporting line.
- 🟡 Branch isolation gaps to know about: `/employees/directory` (names, roles, emails for pickers) is still company-wide for founder/HR/manager/employee, `/departments` counts are company-wide, and leave-request notifications for people without a manager go to all HR/founders regardless of branch.
- 🟡 Not clicked through in a browser (API-tested only): manager Team dialog, HR's branch-restricted views, board-member permission toggles in the UI, branch edit/deactivate dialogs.
- Design choices to confirm: peers in the same branch may chat; only founders create/promote managers and HR (HR can only create employees); board members cannot be assigned to branches.

## Projects and tasks enhancement (migration 0009)
- ✅ **Projects**: code (unique; `PRJ-0001` generated when blank; existing projects backfilled), category, client / business unit, risk level, visibility, estimated effort, tags, completion date (set and cleared with the status). Task hours are summed per project. List filters: risk, category, search by name or code.
- ✅ **Visibility**: `restricted` (default, unchanged rules) or `company` (read-only for everyone in the owner's branch scope; never writable, never across companies; board members excluded).

- ✅ 27 new backend tests (`tests/test_projects_tasks_fields.py`); one existing workflow test updated for the new rejection behaviour. Migration 0009 up/down/up verified on SQLite. Project form, board (new column, type and label badges, hours), and the request-changes dialog checked in a browser as manager.
- ✅ Playwright e2e suite re-run after these changes: 195 passed (192 existing + 3 new in `e2e/tests/f25-project-task-fields.spec.ts`). One existing test (F06-N1) was date-dependent and failed on Mondays; fixed.

## Known limitations / design trade-offs
- Single backend process (in-memory WebSocket fan-out, rate limiter, webhook worker) — see README "Scaling limits"
- Business logic lives mostly in routers; only leave/webhooks/notifications have separate service modules and there is no repository layer
- Leave and the holiday calendar still assume a Monday-Friday week (holidays on Saturday/Sunday are rejected); attendance uses each branch's own working week, so the two can disagree for a branch that works Sunday-Thursday. The dashboard's "present today" count still uses the UTC date
- WebRTC mesh is limited to 8 participants
- Browser sessions live in httpOnly SameSite=Strict cookies bound to the browser (no tokens in web storage); API clients use bearer tokens

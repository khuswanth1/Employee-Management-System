## Findings

### P0 — security
1. **No server-side session revocation.** `POST /auth/logout` only cleared cookies; a copied access/refresh token stayed valid for 30 min / 7 days.
   Refresh tokens were stateless and reusable. Changing a password or an HR/founder password reset did **not** end other sessions. *(fixed, see below)*
2. **PII in logs.** Failed/successful sign-ins logged the email address at WARNING/INFO, and startup logged every tenant user's email, role and
   active flag. An old `backend/auth_activity.log` (email + password length per attempt, 155 KB) sits in the working tree; it is git-ignored but the
   folder is not a git repository yet, so nothing protects it. *(log statements fixed; the stale file needs your decision, see "Left for you")*
3. **WebSockets authenticate once.** An open `/ws` or meeting socket stayed alive after logout, password reset, suspension or token expiry. *(fixed in 2b)*
4. **Rate limiting was per process and memory-only**; several instances multiplied the allowance. *(fixed in 2e with optional Redis; still disabled when `ENVIRONMENT=development`)*
5. **No MFA, password reset by email, or email verification.** *(fixed in 2c, platform admins in 2d)*
6. **Uploads used a deny-list** of extensions and no content check. *(fixed in 2b: allow-list + magic-byte check; downloads were already `attachment` + `nosniff`, my first reading was wrong)* Still no virus scanning.
7. Login without a company slug probes **every** active tenant database (cost grows with tenant count, and tenant slugs are enumerable by timing). *(open)*
8. Bootstrap re-applies `BOOTSTRAP_ADMIN_PASSWORD` to the platform admin on **every start** — a leaked `.env` is a permanent admin credential. *(open, by design today)*

## Log

### Phase 2a — server-side session revocation (done)
Design: every token carries `sv` (the user's `session_version`) and a `jti`.
* A request is accepted only if the token's `jti` is **not** on the platform-DB denylist (`revoked_tokens`, pruned after expiry) **and** `sv` equals the user's current `session_version`.
* `POST /auth/logout` denylists the presented access token and the refresh token (cookie, or `refresh_token` in the body for API clients) — only that session ends.
* `POST /auth/logout-all` and `POST /auth/platform/logout-all` bump `session_version` — every device ends.
* Changing your own password and an HR/founder password reset bump `session_version`; the browser that changed the password gets fresh cookies.
* `POST /auth/refresh` now rotates: the used refresh token is denylisted, so a stolen refresh token is single-use, and an access token is rejected as a refresh token.
* Storage: platform migration `0002` (`platform_users.session_version`, `revoked_tokens`), tenant migration `0010` (`users.session_version`). Both are additive and idempotent; **existing tenants need `POST /platform/migrate`** and existing tokens (no `sv`) keep working until they expire.
* Cost: one primary-key lookup in the platform DB per authenticated request (the platform DB is already read on every request for the company row).
* Known limit: refresh rotation has no "reuse = theft" family kill, because two truly simultaneous refreshes from one browser would then sign the user out.
* Files: `app/core/security.py`, `app/core/session.py`, `app/deps.py`, `app/modules/auth/router.py`, `app/modules/employees/router.py`, `app/db/platform_models.py`, `app/db/tenant_models.py`, `app/main.py`, `alembic_platform/versions/0002_*`, `alembic_tenant/versions/0010_*`, `tests/test_session_revocation.py`.

### Phase 2b — WebSocket session re-validation and upload allow-list (done)
* `/ws` and `/meetings/ws/{room}` start a watcher that re-runs the full token check (signature/expiry, denylist, `session_version`, active account, active company) every `WS_RECHECK_SECONDS` (30). A failed check closes the socket with code 4401, which the existing frontend already treats as "sign in again". Cost: one platform-DB read + one tenant-DB read per open socket per 30 s.
* Uploads (employee documents, task attachments) accept only: pdf, png, jpg/jpeg, gif, webp, docx/xlsx/pptx, doc/xls/ppt, txt/csv/md. The bytes must match the extension (magic bytes; text must be UTF-8 without NUL). `.html/.svg/.js/.exe/.jar/no extension` etc. are refused with 400. **Behaviour change:** other extensions that used to be accepted (e.g. `.zip`, `.json`, `.mp4`) are now refused; extend `ALLOWED_EXT` in `app/storage.py` if you need them.
* Tests: `tests/test_ws_and_uploads.py` (32 cases): socket closes after logout / password reset / offboarding, stays open while healthy, meeting socket closes after logout, a room id from another company is `not_found`, allowed/forbidden/mismatched uploads, task attachment rules + download headers, cross-tenant document access.
* Files: `app/storage.py`, `app/modules/notifications/router.py`, `app/modules/meetings/router.py`.

### Phase 2c — password reset, e-mail verification, TOTP MFA (done for company users)
* **Reset by e-mail:** `POST /auth/password-reset/request` always answers 202 with the same body and sends the mail after the response (no account enumeration by content or timing); 5 requests / hour per IP+address. `POST /auth/password-reset/confirm` takes `{company_slug, token, new_password}`; tokens are random 256-bit, stored only as SHA-256, single use, expire after `PASSWORD_RESET_MINUTES` (60), and a newer request voids older ones. A successful reset ends every session (`session_version`), marks the address verified, and does **not** switch MFA off.
* **E-mail verification:** `POST /auth/verify-email/request` (signed in, one per minute) and `/confirm`. It is informational (`email_verified` on `/auth/me`); sign-in is **not** blocked on it, because that would lock out every existing account.
* **MFA (TOTP, RFC 6238, no new dependency):** `/auth/mfa/setup` → `/auth/mfa/enable` (returns 10 one-time recovery codes, stored hashed) → `/auth/mfa/disable` (needs password + code). Sign-in with MFA returns `{mfa_required, mfa_token}` and **no cookies/tokens**; `POST /auth/mfa/verify` finishes it. The `mfa_token` is a 5-minute JWT of its own type, usable once; wrong codes are limited per account (5 / 15 min) so requesting a new `mfa_token` does not reset the count; a TOTP time step can be accepted only once (replay guard); the secret is Fernet-encrypted at rest. `POST /employees/{id}/mfa/reset` lets HR/founders clear a lost device (HR cannot touch a founder).
* **Migrations:** tenant `0011` (`users.email_verified_at`, `mfa_*`, table `auth_tokens`); run **Companies → Run migrations** after deploying. New settings: `APP_BASE_URL` (origin used in e-mailed links), `PASSWORD_RESET_MINUTES`, `EMAIL_VERIFY_HOURS`. Mail is sent through the existing SMTP settings; **with `SMTP_HOST` empty nothing is sent** (a warning without the link is logged), so reset cannot work until SMTP is configured.
* **UI:** sign-in second step, Forgot/Reset password and Verify e-mail pages, a *Sign-in security* card on My profile (verify e-mail, set up / turn off two-step with recovery codes, sign out everywhere), *Reset two-step* on the employee page.
* **Not done:** MFA for platform administrators (the most privileged account; they still sign in with a password only), forced MFA per company, SSO, a QR code (users paste the setup key or tap the otpauth link), emailing a notice when a password is changed, real SMTP delivery was never exercised (tests replace the mailer).
* Files: `app/core/mfa.py`, `app/core/mailer.py`, `app/modules/auth/account.py`, `auth/router.py`, `auth/schemas.py`, `core/ratelimit.py`, `core/config.py`, `core/security.py`, `db/tenant_models.py`, `alembic_tenant/versions/0011_*`, `employees/router.py`, `tests/test_account_security.py`; frontend `features/auth/*`.

### Phase 2d — MFA for platform administrators (done)
* Same TOTP engine, recovery codes, replay guard and lockout as company users, stored on `platform_users` (platform migration `0003`, applied automatically at startup). Both sign-in routes (`/auth/login` and `/auth/platform/login`) return `{mfa_required, mfa_token}` for an admin with MFA on and set no cookies/tokens until `POST /auth/mfa/verify` succeeds (that endpoint dispatches on the token's role).
* Endpoints: `POST /auth/platform/mfa/setup | enable | disable` (platform-admin tokens only; a company token gets 403). UI: a "Your sign-in security" card at the bottom of the Companies page.
* **Lost device + lost recovery codes:** there is deliberately no web path. A person with shell access to the server runs `python scripts/reset_platform_mfa.py <email>`, which switches MFA off and ends the admin's sessions. Note the existing bootstrap behaviour: `BOOTSTRAP_ADMIN_PASSWORD` in the environment resets that admin's *password* on every start, but never touches MFA.
* Tests: `tests/test_platform_mfa.py` (10 cases, using a second throw-away admin so the shared bootstrap admin keeps working for other tests). Migration 0003 up/down/up run on SQLite.
* Still open: forced MFA per company, SSO, WebAuthn/passkeys.

### Phase 2e — optional shared Redis for several backend instances (done, not run against a real Redis)
Set `REDIS_URL` to turn it on; leave it empty and behaviour is exactly as before (single instance, all in memory).
* **Rate limits** (login, MFA, reset-request, token-confirm): one sorted set per key, hashed (no e-mail/IP in Redis keys), so N instances share one budget; success on any instance resets it. If Redis is unreachable the limiter falls back to the instance's own counter (it never fails open).
* **Live events** (notifications, chat push, task updates): `publish_threadsafe` publishes `{company, users, message}` to one channel (`REDIS_CHANNEL`); every instance's subscriber delivers to its own sockets using the same `(company_id, user_id)` keys, so tenant separation is unchanged. If the publish fails the event is delivered to local sockets only. The subscriber reconnects with backoff; events during an outage are lost (they are persisted separately, the push is a hint).
* **Webhook worker:** each round takes a Redis lock (`SET NX EX 60`, compare-and-delete release), so two instances no longer deliver the same outbox rows twice. If a round takes longer than 60 s the lock can expire mid-round; a duplicate delivery is then possible (receivers should dedupe on `X-WorkSphere-Delivery`, which is already documented). If Redis is down, instances run unlocked.
* **Meetings are not shared.** Signaling rooms stay in one instance's memory, so `nginx.conf` now sends `/api/v1/meetings/ws/<room>` through `upstream api_rooms { hash $uri consistent; }`, i.e. all peers of a room hit the same instance. With more than one backend container you must list each in that upstream (nginx resolves DNS once).
* **Security notes:** all tenants' live events share one channel, so Redis must sit on the private network with a password (`docker-compose.prod.yml` adds a `redis` service with `--requirepass`, no persistence). Do not expose it, and use `rediss://` across hosts.
* **Compose/prod:** also set `APP_BASE_URL` from `PUBLIC_ORIGIN` (it was missing from the prod file; reset/verification links would have pointed at localhost). New required variable: `REDIS_PASSWORD`.
* **Verification:** `tests/test_redis_scaling.py` (15 cases) uses fakeredis to simulate two instances: shared and expiring limits, key privacy, outage fallback, lock exclusivity/expiry, cross-instance delivery exactly once, no leak to another user or company, malformed events, reconnect. **Not verified:** a real Redis server, a second real backend process, the nginx config (`nginx -t`), the compose file build.
* Dependencies: `redis==7.4.1` (runtime), `fakeredis==2.40.0` (dev).

### Phase 4a — attendance engine (done; browser click-through not done)
**Rules** (all in `app/modules/attendance/engine.py`, pure functions with no database or clock):
* A *work date* is the local calendar date in the person's timezone (branch timezone → company `company_timezone` setting → UTC). For an overnight shift it is the date the shift **started**, so 22:00-06:00 is one record, found again after midnight (this was the old cross-midnight bug: check-out looked up "today" and failed).
* Working week = branch `working_days` (default Mon-Fri only when nothing is configured); holidays come from the holiday calendar and win over the week. Weekend/holiday work is all overtime and is flagged (`weekend_work` / `holiday_work`).
* Fixed shifts: late/early only count **beyond the grace period** and are measured from the scheduled time; flexible shifts have neither. Scheduled times are built from local wall-clock time, so DST is honoured (a 22:00-06:00 shift on the night clocks go forward is 7 real hours; tested for Europe/London).
* Worked time = session minus the union of breaks (overlaps merged, breaks clipped to the session, an open break ends at check-out). Status: `present` (>= required hours), `half_day` (>= half-day hours, default half the requirement), `short_day`, `in_progress`.
* **Duplicates/missing check-out:** a second check-in while open is 409; a finished work date cannot be re-opened (use a correction); a session open > 16 h (or > 6 h past a fixed shift's end) is closed automatically at the scheduled end (or check-in + required hours), flagged `auto_closed`, and the person is told to request a correction.
* **History is frozen:** the day's numbers and the shift id are stored when the session closes, so editing a shift, the holidays or the working week never rewrites past records. Shift assignment affects future check-ins only.

**API** (`/attendance`): `POST check-in {work_mode, lat, lng}` (body optional), `check-out`, `break/start|end`, `today`, `mine`, team list (filter `status`), `summary` (late days/minutes, early departures, half/short days, weekend/holiday/WFH days, auto-closed), CSV with the new columns. `shifts` CRUD + `shift-assignments` (HR/founder; managers read), `geofences` (branch centre + radius + required; office check-ins outside it are refused with 403, missing location 422, **work from home is exempt**; setting `allow_wfh` can switch WFH off). `corrections`: request (naive times are the person's local time; max 24 h; not future; last 60 days; one pending per day), cancel, queue (scoped like every other team view), decision (reject needs a reason; nobody decides their own; managers need the new `attendance.approve` permission, granted by default; out-of-scope requests look non-existent). Approval rewrites the day, drops breaks that no longer fit, marks `source=correction`, notifies the employee and is audited.

**UI:** Attendance page (office/home choice, location prompt only when the branch enforces it, shift and lateness shown, correction dialog and "my requests" with cancel), *Attendance Requests* queue, *Shifts & locations* setup (shift editor, assignment, geo-fence per branch), report columns.

**Verification actually run:** engine 26 tests; API 18 tests (timezone/week, holiday, WFH switch, shift validation + scope, history freeze, overnight across midnight, duplicates, forgotten check-out, geo-fence, correction workflow + permissions, reports, cross-company isolation) using a controllable clock; 12 frontend component tests; migration 0012 up/down/up with an existing attendance row preserved. Existing tests were kept; two expectation lists were extended for the new permission/head revision.

**Known gaps:** selfie verification; rosters/rotating shifts and per-day overrides; absence is not derived (a no-show has no record; leave-aware absence reporting belongs with the leave rewrite); geo-fence is a client-reported position (can be spoofed; treat as a deterrent); the dashboard "present today" and board counts still use the UTC date; leave/holidays still Mon-Fri; PostgreSQL not run for migration 0012 (SQLite only).

### Phase 4b — leave engine (done; browser click-through and Playwright not run)
**Design** (`app/modules/leave/engine.py` pure rules, `service.py` ledger, `router.py` API):
* **Ledger.** Every balance change is a `leave_ledger` row (`grant`, `carry_in`, `adjust`, `use`, `refund`, `expire`, `encash`) and an atomic SQL update of the cached columns on `leave_balances`, in the caller's transaction. Unique constraints `(request_id, kind)` and `(user, type, year, kind, period)` make retries, replays and repeated accrual runs no-ops. The paid-type deduction is a conditional UPDATE ("only if enough remains"), so concurrent approvals cannot overdraw. Decisions and cancellations first claim the request with a compare-and-set on `status`, so two simultaneous decisions cannot both proceed. Invariant, tested: `remaining == sum(ledger.days)`.
* **Days counted** on the person's own working week (branch `working_days`, else Mon-Fri) minus holidays; a type may count calendar days instead. Half day = 0.5, single date only; a half day and a full day (or the same half twice) clash, first + second half do not. Holidays on a day some branch works (e.g. Sunday for a Sunday-Thursday branch) are now allowed; days nobody works are still refused.
* **Policy per type:** `annual_upfront` or `monthly` accrual (quota/12 per month from the joining month, summing exactly to the quota; booked once per period when balances are read), carry-forward cap, optional lapse after month N (unused carried days only, never more than remains), minimum notice, longest stretch, half days on/off, encashable with a yearly cap, active flag.
* **History is never rewritten.** Approved and pending requests keep the days they were counted with when a holiday, the working week or a policy changes. Editing a type's quota no longer silently changes anyone's allocation (it used to): the difference is applied to this year's balances only if HR ticks *apply to current year*, and then as a visible `adjust` entry per person.
* **Requests:** edit while pending (`PATCH`), cancel (approved future leave is refunded exactly once), **revise** approved not-yet-started leave: a new pending request is linked to the original, which stays approved and charged until the revision is approved; approval then supersedes the original, refunds it and charges the revision in one transaction (a rejected revision changes nothing).
* **Delegation:** a manager (with `leave.approve`) delegates their direct reports' approvals to an active manager/HR/founder for up to a year; the delegate sees those requests and is notified of new ones, never decides their own, cannot decide other managers' teams, and the decision records `decided_via`. Revoking takes effect immediately.
* **HR tools:** adjustments (note required, cannot go negative), encashment (type must allow it, yearly cap), `POST /leave/maintenance` (accruals, year-end carry, lapse; idempotent), balances/usage reports + CSV, per-person ledger.
* **Scope fix found on the way:** `GET /leave/balances/{id}` let any HR (any branch) read any employee's balances; it is now scoped like the rest (404 outside your scope).

**Migration 0013** (additive; run *Companies -> Run migrations*): policy columns on `leave_types`, `carried_in/expired/encashed` on `leave_balances`, `half_day/supersedes_id/decided_via` on `leave_requests`, tables `leave_ledger` and `leave_delegations`. Existing balances are seeded into the ledger as `opening` entries so the invariant holds from day one; verified up/down/up on SQLite with legacy balances and an approved request (all preserved).

**Verification actually run:** 10 engine tests; 23 API/service tests (half days, branch weeks, calendar-day types, notice/stretch, edit, ledger reconciliation, double charge/refund no-ops, two simultaneous approvals charge once, overdraw guard, revision swap and reject, delegation window and limits, policy changes not touching history, inactive types, monthly accrual once per month, carry-forward + expiry with idempotent reruns, adjust/encash limits, scope, holiday rule, reports, cross-company isolation); 15 new frontend component tests.

**Known gaps:** no scheduler (see above); accrual is evaluated at "today", so a type with monthly accrual cannot be used for dates beyond what has accrued; a revision cannot span a year boundary (same rule as new requests); delegation covers a manager's direct reports only, not HR/founder scope; leave is still not shown on the attendance/absence reports; encashment has no payroll link; PostgreSQL not run for migration 0013 (SQLite only); the concurrency test uses SQLite, which serialises writers, so it demonstrates the compare-and-set logic but is not a PostgreSQL row-lock test.

### Phase 7a — payroll (done)
**What exists** (`app/modules/payroll/`: `engine.py` pure Decimal arithmetic, `service.py` builds inputs from leave/attendance/calendar, `router.py`):
* **No statutory rules are built in.** Tax, social-security, pension and similar rules differ by jurisdiction and change; inventing them would be wrong. Every earning/deduction is a *component* the company defines (fixed, % of basic, or % of gross for deductions; optional monthly cap; note for the source of the rule). The UI says so wherever components are edited. **Before production use the rates must be taken from the authority's current official rules and checked by someone qualified.**
* **Money:** integer minor units (two decimals assumed) and basis points, Decimal arithmetic with half-up rounding; no floats stored.
* **Pay structures** are versioned (`compensations` + lines): a change is a new version from a chosen date, earlier versions stay, and a version cannot start inside a month whose payroll is approved. The audit log records that pay changed, never the amounts.
* **Pay for a month:** working days come from the person's branch week minus holidays; hire/leave dates prorate; approved **unpaid** leave reduces pay, paid leave does not; with the setting `payroll_attendance_basis = attendance` only days worked (present 1, half day 0.5, short day 0) plus paid leave are paid; `payroll_overtime_multiplier > 0` pays overtime hours at (basic / (working days x standard hours)) x multiplier (default 0 = not paid). The policy used is stored on the run. Components marked prorate shrink with unpaid days.
* **Workflow:** HR/founder creates a run (calculates drafts) -> may add one-off adjustments -> submits -> a **different** person approves (or sends back with a reason) -> mark as paid (record only; no money moves). Negative net pay blocks approval. Approved payslips are frozen snapshots: later changes to pay, names, components or settings do not touch them; approved runs cannot be recalculated or cancelled.
* **Access (server-side):** founder everything; HR without a branch everything except the pay of founders, board members and other HR; HR with a branch only employees/managers of that branch and no run management; managers, board members and employees have no payroll access except reading their **own** payslips once approved. Opening someone else's payslip or pay history is audit-logged. Tenant isolation is by database.
* **Reports/exports:** per-run totals and by department, per-person history, yearly summary, CSV per run (scoped like the screen).
* **Settings:** `payroll_currency`, `payroll_attendance_basis`, `payroll_overtime_multiplier` (Administration page). Currency is stored per pay structure; there is no conversion between currencies.

**Migration 0014** (additive; run *Companies -> Run migrations*): `salary_components`, `compensations`, `compensation_lines`, `payroll_runs`, `payslips`, `payslip_lines`. Up/down/up verified on SQLite.

**Verification actually run:** 14 engine tests (proration, unpaid/paid leave, attendance basis, caps, overtime, negative net, adjustments, rounding); 15 API tests (access matrix for founder/HR/branch HR/manager/employee/board, versioned pay + validation, exact figures for full month / unpaid leave / paid leave / joiner / leaver / Sunday-Thursday branch, adjustments, submit/approve separation, send-back, freeze after approval, negative-net block, cancelled months, attendance basis + overtime, HR not seeing founder/HR pay in runs or CSV, history/summary, cross-company isolation); 14 frontend component tests; Playwright: HR sets up pay and a run, a founder approves, the employee reads the payslip, plus access checks; new pages in the accessibility sweep.

**Known gaps:** no statutory rules (by design); no bank payment file, payroll tax filing, year-end statements, loans/advances schedule, arrears or retro-pay (a changed past pay needs a manual adjustment), unpaid leave is deducted on working days only, mid-month pay changes use the structure in force on the last day of the month (no split), encashed leave days are not paid out automatically, one currency per structure, PDF is the browser's print dialog (no server-side PDF), PostgreSQL not run for migration 0014.

### Phase 7b — performance management (done)
**Model** (`app/modules/performance/`; `rules.py` holds the pure parts): `rating_scales` (2-10 named levels; a 5-point default is created on first use), `performance_cycles` (draft -> active -> closed; dates, optional due dates, competency list = the appraisal form, a scale), `goals` (objective or KPI, weight %, target/current value, progress, status proposed/agreed/cancelled), `goal_updates` (check-ins), `performance_reviews` (one per person per cycle), `feedback`. Migration `0015`, additive; run *Companies -> Run migrations*.
* **Cycle:** HR/founder create it (scale and competencies are locked once it starts), then *Start* opens a review for every active employee, manager and HR person who joined before the cycle ends (founders and board members are not reviewed) and notifies them. *Close* freezes goals, reviews and progress; a closed cycle stays readable. Reminders go to people whose part is still open.
* **Goals:** weights of a person's non-cancelled goals add up to at most 100. A goal you set for yourself is *proposed* until your manager agrees it (agreed at once if you have no manager, or if a manager/HR sets it). Once agreed, only the manager/HR edits or cancels it; the owner can withdraw their own unagreed proposals. KPIs take a current value (progress = current/target, capped at 100); objectives take 0-100 progress. Progress can only be recorded on agreed goals in an active cycle.
* **Appraisal workflow:** `pending_self` -> (employee submits: overall rating, comments, every competency rated) `pending_manager` -> (reviewer submits: overall rating, assessment >= 10 characters, every competency rated; optional per-goal ratings give a weighted goal score) `completed` -> (employee acknowledges, optionally with a response) `acknowledged`. The manager part opens only after the self review is submitted. Ratings must be on the cycle's scale.
* **Confidentiality, enforced in the API:** goals and reviews are visible to the owner, the owner's line manager and the reviewer, and HR/founders in scope; colleagues, other teams' managers and the board get 404. A draft self review is private to its author. The manager's rating and comments are hidden from the employee until the manager submits. The reviewer is the line manager when the cycle starts; if there is none (or they left) HR/founders in scope write the review, and HR can reassign the reviewer while it is open. Opening someone else's review, history or feedback-about is audit-logged.
* **Feedback:** praise or constructive, to any active colleague; a "private to their manager" option hides it from the subject while their manager and HR in scope can read it.
* **Reports:** per cycle (scoped: founder all, HR their scope, a manager their team): participants, status counts, self/manager completion, overdue counts, average self and manager rating, rating distribution on the scale, average by department, goal count/progress; CSV for HR/founders. Only submitted manager ratings count.
* **UI:** Performance page with *My review* (review status, goals, self review form, shared review, acknowledge), *Team* (summary tiles, reviews table, manager form, a person's goals with Agree), *Feedback* and *Cycles* (create, start, remind, close, summary, CSV).

**Verification actually run:** 5 rules tests; 14 API tests (scales/cycles validation and permissions, activation eligibility, goal agreement/weights/withdrawal, KPI progress, self-review validation and draft privacy, the full cycle with the manager part hidden until submitted, scope for colleagues/other managers/board, reviewer-less reviews and reassignment, reminders + scoped summaries + CSV, closing freezes everything, feedback visibility, cross-company isolation); 14 component tests; Playwright: HR starts a cycle, employee proposes a goal, manager agrees, both complete their reviews, the employee acknowledges, the API proves the unsubmitted manager review is hidden, plus negative access checks; `/performance` is in the accessibility sweep. **The browser test found a real crash** (the Team tab dereferenced its data while its query was still waiting for the cycle); fixed, with a component regression test that fails without the fix.

**Known gaps:** no peer / 360 or upward reviews; no calibration step (the manager's rating is the final rating); goals and ratings are not linked to pay or promotion (deliberately); KPIs assume higher is better; no email notifications beyond the in-app ones (the existing SMTP path sends them if configured); PostgreSQL not run for migration 0015.

### Phase 3a — employee lifecycle and organisation chart (done)
**Model:** `employee_events` (append-only: kind, effective date, before/after values, note, who). Migration `0016` backfills one `joined` row per existing person (dated with their hire date) so every history starts somewhere; new people get `joined` when created (and founders at provisioning). Run *Companies -> Run migrations*.
* **Actions** (`/employees/{id}/lifecycle/...`, HR within their branch and founders; each validated, audited, and notifying the people affected): promotion (title, job level; a role change is founder-only and ends the person's sessions), transfer (department, reporting manager, branch -> founder only; one event per thing that changed; branch/manager consistency and reporting loops are refused; teams are adjusted as before), probation set/extend and confirmation, suspension (signs the person out at once and blocks sign-in; record, work and team stay; reason visible to HR/founders only) and reinstatement, resignation (the person submits their own, HR/founders can record one on their behalf; warns when shorter than the notice period; can be withdrawn and resubmitted), reactivation of a former employee (history kept; a new joining date can be recorded; respects the plan's user limit).
* **Changes apply immediately.** `effective_date` (today or earlier, not before joining) is recorded for the history; nothing is scheduled for the future, and nothing offboards someone automatically on their last working day — the worklist shows who is due and HR offboards from the record.
* **Offboarding** now takes an optional reason, records `offboarded`, and ends the person's sessions. Completing every exit-clearance checklist item records `exit_cleared` once; the history shows how far clearance is.
* **Existing edits are captured:** changing department, manager, branch, role or title on the employee form writes the same events (field-only edits such as a phone number add nothing).
* **Visibility:** the history is readable by the person, their line manager and the administering HR/founders; `suspended`, `reinstated` and `exit_cleared` are internal (HR/founders only). Colleagues, other teams' managers, other branches' HR and the board get nothing. HR never sees founders' or board members' history.
* **Worklist / feed (HR, founders):** `GET /lifecycle/due` (probations ending and not confirmed, leavers with their last day, exit clearance still open; overdue flagged) and `GET /lifecycle/events` (filterable, scoped to the HR user's branch).
* **Org chart:** `GET /org/chart` returns the reporting tree of active employees, managers, HR and founders (no contact data), filterable by department/branch; people whose manager is outside the filter appear as roots; cycle-safe; the board has no access. UI: collapsible tree with team sizes and links to profiles.
* **Payroll interaction fixed:** a suspended person is still employed, so payroll runs keep paying them (previously anyone not active was skipped).
* **UI:** *History* tab on the employee record (timeline + actions that fit the person's state), *Resignation* card on My profile, *Lifecycle* worklist/activity page (HR/founders), *Org chart* page.

**Verification actually run:** 15 API tests (history privacy, who may act, promotion before/after + role founder-only + session end, transfers incl. branch/manager/loop rules, form edits recorded, probation/confirmation + worklist, suspension immediacy + internal visibility, suspended-in-payroll, resignation flows incl. notice warning, offboarding + exit clearance + return, scoped feed, org chart, cross-company); 14 component tests; Playwright: HR promotes (before/after shown), suspends (the employee's open session ends, sign-in refused) and reinstates, the manager sees the history but not the suspension, an employee resigns and withdraws from My profile while HR sees it on the worklist, the org chart updates when someone is offboarded, plus negative access checks; `/org-chart` and `/lifecycle` are in the accessibility sweep. Migration up/down/up on SQLite with backfill.

**Known gaps:** no future-dated changes or automatic offboarding; no e-mail reminders for probations (in-app notifications only for the actions themselves); no approval chain for promotions; history rows cannot be corrected (by design: add a new event); PostgreSQL not run for migration 0016.

### Phase 6a — private meetings and calls (done)
**Problem:** any signed-in user of a company could open any meeting room whose id they knew, and every meeting was effectively for everyone. **Now** a meeting belongs to its host and the people invited.
**Model:** `meeting_participants` (meeting, user, invited by) and `meetings.kind` (`meeting` | `call`); migration `0017` (up/down/up checked on SQLite). Run *Companies -> Run migrations*. **Meetings that already existed get no participant rows, so they become host-only**; the host can invite people afterwards.
* **Who can be invited:** one person, a chosen set, a team (you must belong to it as member, leader or manager; HR/founders may use any team) or a chat group (you must be in it). Everyone is filtered by the chat communication hierarchy and must be active; naming a person you cannot contact is refused (403) and people pulled in by a team/group who cannot be contacted are left out and listed in `skipped`. Up to 100 people.
* **Calls:** `POST /meetings/call` creates a private two-person room and notifies the other person ("Incoming call", kind `call`); ringing the same person again returns the open call. A call cannot take more people.
* **Host controls:** only the host adds people; the host removes anyone, and anyone may remove themselves; removing someone disconnects them from the live room (`removed`, close code 4403) and they cannot return. The host or a founder/HR ends a meeting; an administrator ending someone else's meeting is audited.
* **Privacy:** anyone not host/invited gets 404 on the room, the list and the WebSocket (existence is not revealed), including HR and founders. **Behaviour change:** earlier an uninvited user got 403 on ending a meeting; now 404 (existing tests updated accordingly). Rooms stay keyed by company, so other companies cannot reach them.
* **UI:** *Call someone* dialog (searchable, one person), *New meeting* dialog with a searchable people list plus your teams and chat groups, a *With* column and Call badge on the list, and an *Invited people* panel in the room (host: Invite more / Remove; guests: read-only).
* **Bug found and fixed on the way:** `Modal` re-ran its focus logic on every parent render, which moved focus to the close button, so typing more than one character into a modal whose form state lives in the page lost focus (and a space then pressed the close button). Playwright's `fill` had hidden it. The effect now depends only on `open`; vitest and Playwright type with real keystrokes.

**Verification actually run:** 12 new API tests (private-by-default, one person, a chosen set, chat groups and membership rule, teams and HR, hierarchy refusals, skipped people, one-to-one call incl. reuse and notification, host-only add/remove and rejoin block, kick of a live connection, ending/audit, cross-company); realtime tests adjusted; 7 component tests; 5 Playwright tests including a real two-browser call with fake camera/microphone where both sides render the other's live video, a removed guest being disconnected, and an uninvited employee being refused. Full runs: vitest 113 passed, Playwright 256 passed.

**Known gaps:** no recurring meetings; no e-mail/calendar invitation; the other person is notified in-app (and by WebSocket push) but nothing rings a closed browser; mesh WebRTC still limited to 8 per room (no SFU/TURN beyond the configured ICE servers); teams the caller does not belong to cannot be invited by managers/employees by design; PostgreSQL not run for migration 0017.

### Phase 6b — chat media, stickers, reactions, voice and calls (done)
**Model (migration `0019`, run *Companies -> Run migrations*):** `messages` gains `kind` (text | image | audio | file | sticker), file name, stored name, size, content type and duration; new table `message_reactions` (message, user, emoji). Existing messages become `text`.
* **Files:** `POST /chat/conversations/{id}/attachments` (multipart). Allowed: png, jpg, gif, webp; mp3, wav, ogg/opus, m4a; pdf, Office documents, txt/csv/md; `.webm` only as a declared voice recording. The bytes must match the extension; maximum 25 MB; anything else (html, svg, exe, zip, scripts) is refused with 400. The same membership and communication-hierarchy rules as text apply on every send.
* **Serving:** `GET /chat/messages/{id}/file`, members of the conversation only (404 otherwise). Images and audio are served inline with their own content type, `nosniff` and a sandboxing CSP; documents are always `attachment` and `application/octet-stream`.
* **Stickers:** a fixed set of 24 listed by `GET /chat/stickers`; `POST .../stickers` accepts only those ids (422 otherwise). **Reactions:** `POST /chat/messages/{id}/reactions` toggles one of 8 emoji; every member is pushed the updated message over the existing socket.
* **UI:** emoji picker with categories (inserts at the caret), attach menu (photo / document / music), sticker picker, microphone button that records with `MediaRecorder` (max 5 minutes, timer, cancel / send), image and audio players, download for documents, reaction pills, conversation-list previews ("📷 Photo", "🎤 Voice message", "🎉 Sticker").
* **Calls:** *Call* and *Video* in the conversation header. In a 1:1 chat they open the private call from phase 6a (the other person is notified); in a group they start a meeting for that group. A voice call opens with `?audio=1` and joins with the microphone only (the camera button reads "No camera").
* **Verified:** 16 API tests (safe types and mismatches refused, size limit, inline vs download headers, strangers, cross-rules, stickers, reactions, live push); 17 component tests; 5 Playwright tests in real Chromium with a fake microphone and camera (two people exchange emoji, a decoding photo, a downloadable PDF, playable audio, a sticker, live reactions, a recorded voice message, voice and video calls); migration 0019 up/down/up on SQLite. Two accessibility contrast failures found by the browser test were fixed.
* **Not built / limits:** no editing, deleting or forwarding of messages, no search, no GIF search, no read receipts, no virus scanning, files are stored on local disk like other uploads (object storage and quotas are still open), voice recording needs HTTPS or localhost and a microphone, WebRTC calls remain a mesh limited to 8 people, and PostgreSQL was not run for migration 0019.


### Phase 6c — chat and calling overhaul (done; migration `0020`)
Builds on 6a (private meetings) and 6b (media, stickers, reactions). Run *Companies -> Run migrations* for migration `0020`.

**Data (migration 0020, all additive):** `messages` gains `reply_to_id`, `edited_at`, `deleted_at`; `conversation_members` gains `pinned` and `last_delivered_message_id`; `users.last_seen_at`; `meetings` gains `call_video`, `answered_at`, `ended_at` and `outcome` (answered | declined | missed). Existing rows keep working (replies empty, nothing pinned, calls without outcome are treated as ringing/missed by age).

**Messaging API:** replies (`reply_to_id` on text, sticker and attachment sends; the target must be a live message of the same conversation), `PATCH /chat/messages/{id}` (sender only, text or caption, shown as "edited"), `DELETE /chat/messages/{id}` (sender only, soft delete: text, file and reactions are removed, a placeholder stays so replies still make sense), `PUT /chat/conversations/{id}/pin` (personal, at most 5), `GET .../messages?before_id=&limit=` (paged, newest first) and `?q=` (search inside one conversation, wildcards escaped), `GET /chat/presence`, conversation payload now carries each member's `last_read_id` / `last_delivered_id` and `pinned`. Stickers carry a category (`Reactions`, `Celebrate`, `Work`, `Fun`).

**Live events (existing `/ws` socket, tenant-scoped, only to people who share the conversation):** `chat` (new / edited / deleted / reaction), `chat_read`, `chat_delivered` (the other person's browser acknowledges what it received, including messages that arrived while it was offline), `chat_typing` (client signal, one per 1.5 s per conversation, membership checked), `presence` (online/offline with last seen), `call` (ringing), `call_ended`.

**Calls:** `POST /meetings/call {user_id, video}` rings the other person's open pages; `POST /meetings/{room}/decline`; the first person to join answers it (other devices stop ringing); the caller ending it, closing the page, or 60 s of silence records a **missed call** with a notification; `GET /meetings/calls/history` (direction, voice/video, outcome, talk time). Rooms stay private to the two people (see 6a).

**WebRTC hook rewritten (`useMeeting.js`):** per-peer connection state; the call says "connected" only when media can flow; "Calling…", "Connecting…", "Reconnecting…", "Connection failed"; ICE restart by the side that made the offer; signaling socket reconnect with back-off; quality sampling from `getStats` (good / fair / poor); microphone, camera and speaker selection, camera switch, picture-in-picture and fullscreen where the browser supports them; screen share needs a camera call; every track and connection is released on leave, unmount and `pagehide`. A bug I introduced while rewriting it (a cancelled React effect run opened a second socket, so each person appeared twice) was caught by the two-browser test and fixed.

**UI:** sidebar with profile and connection state, search, online-now strip, pinned and recent sections, presence dots, typing in the list; header with avatar, online / last seen / typing, in-conversation search, voice and video call buttons and a menu (pin, photos, call history); message list paged with "Load earlier messages" (scroll position kept), day separators, reply quotes (click to jump), edit / delete / copy / react / reply toolbar, ticks (sent, delivered, read); composer with emoji picker (search, categories, frequent, recent, arrow-key navigation), sticker picker (search, categories, recent, favourites), like button, attach menu, several files at once with previews, drag and drop onto the chat, validation, per-file progress, cancel and retry; voice recorder with pause / resume, timer, preview, delete and send; audio player with seek, speed, volume, waveform (voice messages), and one-at-a-time playback; full-size photo viewer with navigation and download; incoming-call overlay (accept / decline, ringtone) on every page; room page with status, duration, quality and a layout where your preview never covers the other person.

**Verification actually run:** 20 + 7 API tests (replies, edit, delete incl. file removal, pins, search, paging, delivered/read marks and their live events, typing audience and rate limit, presence, call ringing, decline, answered, missed three ways, history paging and isolation); 100+ component tests (bubble actions, ticks, audio player, pickers, viewer, composer queue / progress / cancel / retry, recorder hook with a fake MediaRecorder incl. permission denied, empty recording, maximum length and unmount clean-up, chat page, incoming call); real-browser tests with two authenticated users and a fake camera and microphone: replies / edit / delete live, ticks moving sent → delivered → read, typing and online → last seen, pin saved, search, emoji recents, sticker favourites surviving reload, like, drag-and-drop of four files with thumbnails, upload cancelled (nothing reaches the server), photo viewer and download, two audio players never playing together, 70 messages paged, an incoming call ringing on another page and **not** on a bystander's, accept → both sides "Connected" with a running timer, mute shown to the other side, remote audio track live, hang-up releasing every track, decline, missed call, a video call with decoded video on both sides and no overlap, signaling cut and recovered, strangers refused. Migration `0020` up / down / up on SQLite.

**Redis / scaling:** chat, presence, typing, ringing and delivery events go through `publish_threadsafe`, so with `REDIS_URL` every instance delivers them. Two limits remain: *presence* (`/chat/presence` and the online flag) is computed from the sockets held by the instance that answers, so with several instances a person connected elsewhere can show offline until their next event; and *WebRTC signaling rooms* are per instance, so the two people of a call must reach the same instance (the nginx `api_rooms` stickiness). A Redis presence key per user and a Redis-backed room registry would remove both.

**Deployment requirements:** HTTPS (or localhost) for camera, microphone and screen sharing; a **TURN server** (`TURN_URL`, `TURN_SECRET` or username/credential, see `.env.example`) for people behind restrictive networks, since STUN alone does not connect them; keep WebSocket upgrade and sticky routing for `/api/v1/meetings/ws/`; run migration 0020.

**Not built or not verified:** video file sharing (the existing upload rules do not allow video); end-to-end encryption; message forwarding; per-person switch for read receipts or "last seen"; group delivery shows "delivered/read" only when every member has it, with no per-member detail; edits have no time limit; TURN and ICE restart under real packet loss were not exercised (only a signaling reconnect with a local network); network-quality labels were seen as "good" only; speaker selection and picture-in-picture depend on the browser (Chromium / Safari); the waveform is skipped when the browser cannot decode the file; PostgreSQL was not run for migration 0020.
